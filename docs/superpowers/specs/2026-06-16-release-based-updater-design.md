# Release-Based Updater Design

## Context

The current hidden updater app downloads files from a Git branch using the
GitHub contents API and raw file URLs. This makes the device update from a
moving branch state, requires repository tree scanning on the M5Dial, and does
not match the desired release workflow.

The project runs on M5Stack Dial with UIFlow2/MicroPython. The updater is a
hidden app launched at boot when the setup portal stores an update request flag
in NVS. This design keeps that startup flow, the lazy updater app loading, the
simple progress screen, and i18n display strings.

## Goals

- Update only from GitHub Releases, never from branches.
- Default to stable releases.
- Allow pre-release updates through a persistent configuration setting.
- Keep the device-side updater small and memory-conscious.
- Avoid downloading docs, firmware, examples, and other non-runtime files.
- Preserve the existing portal-triggered hidden updater flow.

## Non-Goals

- Updating the base UIFlow2 firmware image.
- Supporting arbitrary repositories or branches from the device.
- Adding an interactive release picker on the M5Dial.
- Installing GitHub source archives directly.

## Configuration

Replace the current branch setting with a release channel setting:

```python
UPDATE_CHANNEL = "stable"
```

Allowed values:

- `"stable"`: install the latest non-draft, non-prerelease GitHub Release.
- `"prerelease"`: install the newest non-draft GitHub Release marked as a
  pre-release.

`UPDATE_BRANCH` is no longer used. If it exists in an older `config.py`, the
new updater ignores it. The setup portal removes the editable branch field and
adds a persistent release channel selector.

The updater may also track the installed version in a small local state file,
for example `storage/update_state.json`, with the installed tag and channel.
This state is informational and must not block manual update requests.

## GitHub Release Selection

Stable mode uses GitHub's latest release endpoint:

```text
GET https://api.github.com/repos/bnbbrewers/UltimateHomebrewingScale/releases/latest
```

GitHub defines this endpoint as the latest published release excluding drafts
and pre-releases.

Pre-release mode lists releases:

```text
GET https://api.github.com/repos/bnbbrewers/UltimateHomebrewingScale/releases
```

The updater chooses the first release where:

- `draft` is false.
- `prerelease` is true.
- The expected update asset is present.

If no matching release or asset is found, the updater reports a localized error
and returns to the launcher after OK.

## Release Asset Contract

Each installable release publishes a device-specific asset generated by the
release process. The device does not install GitHub's automatic source archive.

Recommended asset:

```text
uhs-update-manifest.json
```

The manifest contains the exact runtime files to install:

```json
{
  "version": "v1.2.3",
  "channel": "stable",
  "files": [
    {
      "path": "apps/updater_app.py",
      "url": "https://raw.githubusercontent.com/bnbbrewers/UltimateHomebrewingScale/v1.2.3/apps/updater_app.py",
      "size": 1234,
      "sha256": "..."
    }
  ],
  "delete": ["install.py"]
}
```

The release process is responsible for generating URLs that the device can
download directly. Those URLs must point to the immutable release tag, never to a
branch name. Runtime files include application code, UI code, i18n files, assets,
storage modules, API modules, device modules, web portal modules, `main.py`, and
`config.py.example`. Docs, firmware images, examples, Git files, Markdown, and
development-only files are excluded.

## Device Update Flow

1. The setup portal persists `UPDATE_CHANNEL` and stores `update_requested=1`
   in the `uhs` NVS namespace when the user requests an update.
2. `main.py` sees the update flag at boot and starts `updater_app`.
3. `UpdaterApp` shows the updater screen and calls `core.updater.update()`.
4. `core.updater` ensures Wi-Fi connectivity using the existing Wi-Fi device.
5. It resolves the target release according to `UPDATE_CHANNEL`.
6. It downloads and parses `uhs-update-manifest.json`.
7. It installs files one at a time:
   - create parent directories
   - stream the remote content to `path.tmp`
   - verify size and hash when available
   - replace the destination with the temp file
   - report progress
8. It removes paths listed in the manifest `delete` section.
9. It writes installed release metadata if state storage is available.
10. It clears the NVS update flag.
11. It shows completion and waits for OK before rebooting.

The updater should never erase user configuration such as `config.py`, Wi-Fi
credentials, calibration data, or keg registry data.

## Error Handling

The updater keeps the existing behavior of showing an error and allowing OK to
return to the launcher.

Important errors:

- Wi-Fi connection failure.
- GitHub API failure or rate limit.
- No matching stable/pre-release release.
- Missing update manifest asset.
- Invalid manifest format.
- Download failure for one or more files.
- Size or hash mismatch.
- Filesystem write or rename failure.

The updater writes only through temp files. A failed file download must not leave
a partial destination file in place. If failures occur after some files were
updated, the updater reports the incomplete state and does not claim success.

## UI and i18n

The existing updater screen remains intentionally simple. It should display:

- selected channel (`stable` or `pre-release`)
- target release tag when known
- scan/download/install progress
- final success or localized error

All user-facing labels and errors use the existing i18n locale files.

## Testing

Unit tests should cover release selection and manifest installation without real
network calls:

- stable mode uses `/releases/latest`
- pre-release mode lists releases and chooses the newest pre-release with the
  expected manifest asset
- branch configuration is ignored
- manifest validation rejects invalid or unsafe paths
- file installation writes temp files before replacing destinations
- failures keep the update flag behavior consistent
- portal schema exposes `UPDATE_CHANNEL` and no longer exposes
  `UPDATE_BRANCH`

Existing startup routing tests should continue to verify that an update request
starts `updater_app`.

## Migration

`config.py.example`, portal schema, docs, and translations are updated to use
`UPDATE_CHANNEL`.

Existing devices with `UPDATE_BRANCH` continue to boot. The new updater ignores
that field and falls back to `UPDATE_CHANNEL = "stable"` if no channel is
configured.
